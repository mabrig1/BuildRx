# Cloudflare Workers — deploy apps built with BuildRx

BuildRx prepares a **real generated Next.js project**, including route handlers,
database code and app pages, for Cloudflare Workers. The button **Prepare for
Cloudflare Workers** sends the source (not a marketing HTML mock-up) to the
GitHub repository already linked to the project.

**Preparing is not deploying.** The UI deliberately does not invent a
`workers.dev` URL or claim that Cloudflare accepted an unverified build.

## 1. From the BuildRx workspace

1. Complete your build, resolve blocking errors and confirm its status is **Ready**.
2. Select **GitHub**, connect your GitHub account, and link or create a repository.
3. Select **Deploy → Cloudflare → Prepare for Cloudflare Workers**.
4. The app uploads its own Next.js sources, `wrangler.jsonc`,
   `open-next.config.ts`, an optional GitHub Actions workflow, and
   `CLOUDFLARE-DEPLOY.md` to the linked repository.
5. Follow the links surfaced in the deployment panel.

You do not need to paste a Cloudflare API token into BuildRx to **prepare**
the source. Cloudflare credentials are needed only in Cloudflare or the
GitHub deployment workflow to **publish** the Worker.

## 2. Cloudflare Workers Builds — recommended for ongoing automatic publishing

Open the [Cloudflare dashboard](https://dash.cloudflare.com/) → Workers &
Pages → create/import from GitHub. Connect the prepared repository with your
Cloudflare account and configure:

| Setting | Value |
| --- | --- |
| Runtime | Cloudflare Workers |
| Node | 22 |
| Build command | `npm run cloudflare:build` |
| Deploy command | `npm run cloudflare:publish` |
| Worker name | Value in `wrangler.jsonc` |
| Entrypoint | `.open-next/worker.js` (generated by OpenNext) |

Select the production branch and choose whether to enable deployments on
future commits. If connected to auto-deploy, a later **Prepare** action can
trigger a new build. Keep production secrets only in Cloudflare's Worker
bindings/secrets.

## 3. GitHub Actions — optional manual release

The preparation adds `.github/workflows/cloudflare-deploy.yml`, restricted to
manual `workflow_dispatch`. From the project's GitHub repository:

1. Settings → Secrets and variables → Actions → New repository secret:
   `CLOUDFLARE_API_TOKEN` (limited to Workers deploy permission).
2. Add `CLOUDFLARE_ACCOUNT_ID`.
3. Actions → Deploy on Cloudflare Workers → Run workflow.

The job installs the generated app, builds through OpenNext, and publishes via
Cloudflare Wrangler. It cannot claim success until those steps pass. It
requires a real account and may incur hosting charges under your Cloudflare
plan.

## 4. Why OpenNext instead of vinext here?

These generated projects currently target Next.js 15. OpenNext supports the
existing Next.js 15 codebase, while Cloudflare recommends vinext for new
Next.js 16 projects. Do not auto-migrate an existing app without a compatibility
review. The pinned preparation tool versions are:
`@opennextjs/cloudflare@1.20.15` and `wrangler@4.156.1`.

Official docs:
- https://developers.cloudflare.com/workers/framework-guides/web-apps/opennext/
- https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/

## 5. Release safeguards and limitations

- BuildRx requires a signed-in project owner, passing project status, and a
  GitHub connection before publishing source. Demo-mode projects are excluded.
- Generated `.env`, `.dev.vars`, and untrusted GitHub workflows are excluded.
  Embedded credential-like values block preparation. No secrets are returned
  in the response.
- Existing user-managed Cloudflare config in the generated source is not
  overwritten automatically.
- Pushing into an existing linked GitHub repository updates overlapping
  files there; use a dedicated repository per app. Review branch protections,
  especially when Cloudflare auto-deployment is enabled.
- Workers builds need compatible dependencies and may require additional
  bindings or code changes. Production services (auth, database, payments,
  uploads, notifications) must be configured and tested separately.
- A verified Worker hostname and custom domain are only available **after**
  Cloudflare reports a successful deployment.
- This flow publishes generated **user apps**, not the BuildRx platform itself.
  Hosting BuildRx on Workers is a separate compatibility and deployment task.
